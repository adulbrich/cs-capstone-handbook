You've started using an AI tool on a real project, or one has just handed you a confident answer that turned out to be wrong. This page covers the habits you bring to the tool as an individual: where to spend your attention, what makes delegating the rest reasonable, what not to paste into a tool, and what the research says about how much these tools help. It doesn't cover configuring the tools for a repository (instruction files, hooks, [MCP](https://modelcontextprotocol.io/) servers), which is [AI project setup](/guides/ai-project-setup/), or the norms a team agrees on, which belong in the [working agreement](/guides/working-agreement/#ai-tool-usage).

:::note[tl;dr]
- Validate hard-to-reverse decisions yourself (database schema, authentication, deployment, data migrations, licensing, public interfaces) and delegate easy-to-reverse work freely.
- Delegate only as far as your checks catch: tests, CI, review gates, staging, a rollback path.
- Check every specific fact a tool gives you (a package name, a function signature, a flag, a citation) against its source before you rely on it.
- Don't commit code you can't explain.
- Before you paste partner data, credentials, or meeting content into a tool, check your team's confidentiality rule and the data-use terms of the plan you're on.
- Measure whether a tool speeds you up instead of trusting the feeling: in one randomized trial, developers estimated that AI had cut their completion time by 20% when it had increased it by 19% <Cite id="becker-2025" form="parenthetical" />.
:::

You're responsible for the correctness, security, licensing, and professionalism of anything a tool helps you produce, whoever or whatever wrote the first draft. Treat its output the way you'd treat a pull request from a stranger: consider it, check it, and own what you merge.

## What AI Can and Cannot Do

### What AI helps with

The tools do well where the space of acceptable answers is wide, where you can recognize a good answer faster than you could produce one, and where a wrong answer is cheap to detect. Brainstorming fits all three; a security-critical authentication flow fits none of them.

- Brainstorming ideas and exploring alternatives
- Drafting code, tests, documentation, and plans
- Explaining unfamiliar topics, APIs, or code snippets
- Generating sample data, interaction flows, or boilerplate
- Refactoring, debugging, and code review
- First drafts of writing or implementation

### What AI cannot do well

Some of these limits won't close with a better model, because the information or the responsibility isn't the model's to have. A model cannot apply your project partner's unstated preference, because nobody wrote it down, and it cannot make an ethical call on your behalf, because that call is yours to own.

- Exercise engineering judgment
- Apply your project's specific constraints (your team's architecture, your project partner's requirements, your deployment environment)
- Produce secure, efficient, or trustworthy code without oversight
- Guarantee correctness
- Make ethical decisions

A **hallucination** is fluent, confident output that isn't grounded in anything real: a library that doesn't exist, an API method nobody wrote, a citation to a paper nobody published. The model isn't lying. It generates a plausible continuation of the text so far, and nothing in that process checks the result against the world. Check every specific fact a tool gives you (a package, a function signature, a flag, a citation) against its source before you rely on it; that check is the price of the speedup.

Package names are the best-measured case. <Cite id="spracklen-2025" /> generated 576,000 Python and JavaScript samples with 16 code-generating models and found that, on average, at least 5.2% of the packages recommended by commercial models and 21.7% of those recommended by open-source models didn't exist. That's a security problem as well as a correctness one, because an attacker can publish a malicious package under a name that models keep inventing, and the next person who trusts the suggestion installs it <Cite id="spracklen-2025" form="parenthetical" />.

### Risks

Deal with each of these when the code is written, because none of them fails at the moment it happens. Over-reliance surfaces later as a bug in code nobody on the team can read, and a pasted credential surfaces when someone else uses it.

- Incorrect or misleading information, stated confidently
- Insecure or inefficient code
- Over-reliance: code that nobody on the team can debug
- Confidentiality and intellectual property: what you paste may be retained or used to train the vendor's models (see [Check what you paste](#check-what-you-paste))

## Using AI Effectively

### Start with clear intent

Before asking a tool to generate code, know what you want. "Build the authentication system" is a poor prompt. "Add a login endpoint that accepts email and password, validates against the users table, and returns a JWT" gives the tool enough context to produce something useful. Be this specific because the model fills every gap in your request with its most likely guess, and its most likely guess isn't your design.

### Verify what matters, and build the checks that let you trust the rest

Generated code can look correct while being subtly wrong: off-by-one errors, missing edge cases, insecure defaults, hallucinated library methods. Don't make "read everything it writes" your strategy, though. Generation outpaces careful reading, and a rule you can't keep leaves you with no rule at all once you drop it.

Spend your attention where mistakes are expensive to undo. Database schema, authentication and authorization, deployment topology, data migrations, licensing, and public interfaces are hard-to-reverse decisions: getting one wrong costs far more than the review would have. A feature behind a test suite is an easy-to-reverse decision, because once a test tells you it's broken, the fix is one more commit. Validate hard at the hard-to-reverse decisions and delegate freely elsewhere.

Then make "elsewhere" safe by building the checks. Delegate exactly as far as your checks catch, and no further: tests that would fail if behavior broke, CI running on every pull request, review gates on the paths that are hard to undo, a staging environment, and a rollback path you've actually tried. To hand off more, improve the checks rather than reading harder. The industry report on AI-assisted development from DORA (DevOps Research and Assessment), Google Cloud's research program, found that AI's positive influence on team performance was amplified where developers used their version control's rollback features more often, and the authors suspect that's because undoing changes quickly matters more when work arrives in larger batches, which are harder to review <Cite id="dora-2025" form="parenthetical" />. [Audit Your Safety Net](/activities/ai/#audit-your-safety-net) measures that fit on your own repository.

### Use AI to learn, not just to produce

When a tool generates code you don't understand, ask it to explain the code, then check the explanation against the documentation, because the explanation can be hallucinated as well. Don't commit code you can't debug or modify, whether a model wrote it or a teammate did. The difference between the two is that a teammate can explain their reasoning next week, while a model can't reconstruct reasoning it never had, so the first hard bug in code you accepted without understanding lands on you.

### Know when to stop prompting

If you've gone back and forth with a tool several times on the same problem and the output is still wrong, stop. Read the documentation, look at a working example, or ask a teammate, because another retry with the same context gives the model nothing new to work with, and the documentation or the teammate has what it's missing.

### Check what you paste

Decide what you're about to paste before you paste it, because a vendor's terms decide what happens to it next, and the terms differ by plan. On [OpenAI's plans for individuals](https://help.openai.com/en/articles/5722486-how-your-data-is-used-to-improve-model-performance), for example, ChatGPT conversations and Codex tasks may be used to train its models unless you turn that off in the data controls; its Business, Enterprise, and Edu plans and its API aren't used for training by default. Read the terms for the plan you're on, not just the tool's name.

Sort what you handle into three groups: what may go into any tool, what may go only into tools your project partner has approved, and what never leaves the repository. Meeting recordings and transcripts belong in that sort as much as code and data do. The team writes that rule down once in its working agreement and encodes it for the tools, and [AI project setup](/guides/ai-project-setup/) shows both versions. Your part is to check it before you paste, because the check takes seconds and a leak can't be undone.

## Setting Up AI Tools for Your Project

Configure the tool for your repository before you rely on it, because a tool that knows nothing about your project gives generic answers: the wrong framework, a second way of doing something you already do one way, a dependency nobody agreed to. Project-level instructions, hooks, MCP servers, and skills, committed so every teammate's tool behaves the same way, are the subject of [AI project setup](/guides/ai-project-setup/).

## AI on a Team

Each teammate's tool works in its own context, with no awareness of what the others' tools are doing, so a team without shared norms ends up with inconsistent patterns and code nobody fully understands. The norms (which configuration the team shares, what review generated code gets, how to handle a structural change a tool proposes) belong in the [working agreement](/guides/working-agreement/#ai-tool-usage). The architectural constraints every tool should respect belong in the design document, as [Technical Design in the Age of AI](/guides/technical-design/#technical-design-in-the-age-of-ai) describes.

## AI Coding Tools

The tools change faster than any page about them, so this section names categories and a few current options in each rather than ranking them.

### Chat-Based Assistants

General-purpose models you work with through conversation, useful for brainstorming, explaining concepts, drafting documentation, debugging, and exploring design alternatives.

- [ChatGPT](https://chatgpt.com) (OpenAI)
- [Claude](https://claude.ai) (Anthropic)
- [Gemini](https://gemini.google.com) (Google)

### AI Code Editors and Agents

Tools that integrate into your editor or terminal and can read, write, and modify your codebase. They range from autocomplete assistants to agents that carry out multi-step tasks.

- [GitHub Copilot](https://github.com/features/copilot): code completion, chat, and agent mode in VS Code, JetBrains, and other editors.
- [Cursor](https://cursor.com): a code editor built on VS Code around AI-assisted, multi-file editing.
- [Claude Code](https://code.claude.com/docs/en/overview) and [OpenAI Codex](https://github.com/openai/codex): agentic coding tools that run in the terminal, with IDE and browser versions.

The distinction between autocomplete and agent matters. An autocomplete tool suggests the next few lines as you type, and you see each suggestion before it lands. An agent plans a multi-step change, reads several files, runs commands, and edits your codebase before you see any of it. Give an agent more oversight than autocomplete for that reason, and more again on a team where several people run agents against the same repository.

### Image and Design Tools

Generated images are most useful for placeholder assets and mockups, where the alternative is a grey rectangle. Settle the licensing question before you ship one: read the tool's terms for the plan you're on, because a generated asset in a public repository is a licensing decision whether or not anyone made it deliberately.

- [Midjourney](https://www.midjourney.com), [Stable Diffusion](https://stability.ai), and the image generation built into [ChatGPT](https://chatgpt.com) and [Gemini](https://gemini.google.com): images for mockups, assets, or diagrams.

### AI Search Tools

These sit between a search engine and a chat assistant, returning prose answers with citations attached. The citations are the reason to prefer them for research, and they're also what to check: open each cited link, because a citation can be fabricated, or attached to a source that doesn't say what the answer claims, and you won't see either unless you open it.

- [Perplexity](https://www.perplexity.ai) and ChatGPT's search mode: research and summarization with source citations.

## Choosing the Right Tool

New models arrive often, each with different strengths, and a benchmark ranking tells you little about your own repository. Weigh what matters for your workflow instead:

- Context window: how much of your codebase the tool can see at once. A larger window helps with changes that span many files.
- Speed against quality: a fast model suits autocomplete; a slower, more capable one suits complex reasoning and multi-step changes.
- Integration: whether the tool works with your editor, your terminal, and your version control.
- Cost: many tools have free tiers or student pricing, including the Copilot Student plan above.

If you want to compare models anyway, two public trackers publish current benchmark results: Epoch AI's [Benchmarking Hub](https://epoch.ai/benchmarks) and [LiveBench](https://livebench.ai/).

## Best Practices for Using AI Tools

- Configure the tool for your repository before you rely on it, because everything it produces is bounded by what it knows about the project. [Set Up Your Repository's Skills](/activities/ai/#set-up-your-repositorys-skills) walks through it.
- Decide the hard-to-reverse decisions yourself and delegate the easy-to-reverse ones freely. If you can't tell which is which, [Map Your Hard-to-Reverse Decisions](/activities/ai/#map-your-hard-to-reverse-decisions) before delegating anything.
- Build the checks before you scale delegation: tests, CI, review gates, staging, a rollback path. They're what make a large delegation reasonable instead of a gamble.
- Check your team's confidentiality rule and your plan's data-use terms before you paste anything that isn't your own code.
- Prefer the cheapest tool that does the job, because your checks, not the model, decide how far you can delegate.
- When a tool misleads you, write down what happened and what caught it. The record shows you which of your checks work and where you still need to read.

## Some Truths About AI Tools

Your sense of being faster isn't evidence that you are. In a randomized trial run by METR, an AI research organization, <Cite id="becker-2025" /> had 16 experienced open-source developers complete 246 tasks in mature projects they had worked on for five years on average, with each task randomly assigned to allow or disallow early-2025 AI tools. With AI allowed, tasks took 19% longer. Before starting, the developers forecast that AI would cut their completion time by 24%, and after finishing they estimated it had cut it by 20%. So measure something (time from starting an issue to merging it, the share of generated changes you later revert) instead of trusting the feeling.

The speedup itself depends on who you are and what you're working on, and the evidence points both ways. The METR authors caution against generalizing from their result: their developers knew their large, mature repositories intimately, and the authors note their results are consistent with small greenfield projects or unfamiliar codebases seeing substantial speedup <Cite id="becker-2025" form="parenthetical" />. <Cite id="cui-2026" /> combined randomized field experiments at Microsoft, Accenture, and a Fortune 100 company, 4,867 developers in all, and found that an AI code-completion assistant increased completed tasks by about 26%, with less experienced developers adopting it more and gaining more; each experiment on its own was noisy, and results varied across them. METR has since [written](https://metr.org/blog/2026-02-24-uplift-update/) that it believes developers are likely more sped up in early 2026 than its 2025 estimate, while calling its newer data only very weak evidence for the size of the change, because many developers declined to submit tasks they didn't want to do without AI.

A tool can make you more confident and less careful at the same time. In a user study published at the ACM Conference on Computer and Communications Security (CCS), <Cite id="perry-2023" /> gave 47 participants five security-related programming tasks in Python, JavaScript, and C. The 33 who had an assistant built on OpenAI's codex-davinci-002 model wrote insecure solutions more often on four of the five tasks than the 14 who didn't, and were more likely to believe their code was secure, which the authors suggest means such tools may lead users to be overconfident about security flaws. Participants with secure solutions reported less trust in the assistant than those with insecure ones, and participants who put more work into their prompts, such as supplying helper functions or adjusting parameters, were more likely to reach a secure solution <Cite id="perry-2023" form="parenthetical" />. That model is several generations old, so don't read the size of the gap as current.

The bottleneck moves from writing code to verifying it. When a model drafts the code, your throughput is limited by how fast you can check it, and checking doesn't get faster because generation did: a team that doubles its output with the same review capacity builds a queue of unreviewed changes. The DORA industry report found that AI adoption now improves software delivery throughput but still increases delivery instability, which the report reads as teams adapting for speed before their underlying systems can safely manage AI-accelerated development <Cite id="dora-2025" form="parenthetical" />. Put your effort into the gates in [AI project setup](/guides/ai-project-setup/#hooks-and-gates) before prompt technique.

Everything specific on this page will date quickly. Model names, capabilities, plans, and prices change faster than a guide is revised, and every study above measured tools that have since been replaced. Check the date on a finding before you lean on it, and keep the ability to work without the tool you use today.

## AI Tools in Industry and Academia

Google's CEO told investors in late 2024 that [more than a quarter of all new code at Google](https://blog.google/company-news/inside-google/message-ceo/alphabet-earnings-q3-2024/) was generated by AI, "then reviewed and accepted by engineers". The clause to copy is the last one: the generated code counts only after an engineer has accepted it.

The DORA industry report surveyed nearly 5,000 technology professionals: 90% used AI as part of their work and more than 80% believed it had increased their productivity, yet 30% reported little or no trust in the code it generated <Cite id="dora-2025" form="parenthetical" />. Its central finding is that AI acts as an amplifier, magnifying the strengths of high-performing organizations and the dysfunctions of struggling ones <Cite id="dora-2025" form="parenthetical" />.

The open-source world is more divided. Some projects ban AI-generated contributions outright: [Gentoo's council policy](https://wiki.gentoo.org/wiki/Project:Council/AI_policy) forbids contributing content created with the assistance of AI tools, and [NetBSD's commit guidelines](https://www.netbsd.org/developers/commit-guidelines.html#tainted) presume code generated by a large language model to be tainted and bar it from the repository without prior written approval from the core team. Daniel Stenberg, curl's lead developer, has written about [AI-generated security reports](https://daniel.haxx.se/blog/2024/01/02/the-i-in-llm-stands-for-intelligence/) to curl's bug bounty: they look plausible, so each takes longer to research and discard, and that time comes out of fixing real bugs. If your project contributes to an open-source project, read the upstream's policy before you delegate anything, and expect a maintainer to ask what you verified.

In academia, publishers keep the accountability with people but differ on disclosure. [Nature Portfolio's policy](https://www.nature.com/nature-portfolio/editorial-policies/ai) grades AI use by risk, does not permit assigning authorship or accountability to an AI tool, and asks authors to disclose their use of AI. The [ACM's policy on authorship](https://www.acm.org/publications/policies/new-acm-policy-on-authorship) requires every author to be an identifiable human being and requires AI used to conduct the research, including writing its code, to be described in detail in the paper's methods section, but it no longer requires disclosure of AI used only to help write the paper. If your project's code feeds a paper, record which parts a tool wrote as you go, because a methods section written from memory months later won't be accurate. Universities and employers set their own rules as well, so read the one that governs your work.
