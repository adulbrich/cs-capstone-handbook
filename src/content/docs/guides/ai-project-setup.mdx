Your repository exists, and your teammates have started pointing coding agents at it. Each agent knows only what the repository tells it, so one adds a dependency nobody agreed to and another reports a task finished that nobody can check. This page covers what you commit so every agent works from the same rules and can tell when its work is done. How to prompt and review is the [Generative AI guide](/guides/generative-ai/)'s subject, and the CI (continuous integration) workflow and branch settings belong to [DevOps](/guides/devops/) and [Git and GitHub](/guides/git-and-github/).

:::note[tl;dr]
- What isn't written in the repository doesn't exist for the agent.
- Keep `AGENTS.md` short: commands, conventions the code doesn't show, boundaries, and pointers into `docs/`.
- Give every task a finish line the agent can check: acceptance criteria, a Definition of Done, and tests it runs itself.
- Instructions are requests. Enforce what matters with a hook, a git hook, or CI.
- Commit all of it, and add a line only when the agent has made the mistake it prevents.
:::

## The Repository Is the Agent's Onboarding

A coding agent starts every session with the code, the files you committed, and the task, and nothing else. A decision made in a meeting or a constraint the partner mentioned in an email is invisible to it until someone writes it into the repository. OpenAI's Codex team [makes the same point](https://openai.com/index/harness-engineering/) and treats a versioned `docs/` directory as the system of record.

Birgitta Böckeler [calls](https://martinfowler.com/articles/harness-engineering.html) everything around the model its harness and sorts the parts two ways. Some steer the agent before it acts (she calls these guides); others check the result so it can correct itself (sensors). Each is either computational (a script: fast, and the same answer every time) or inferential (another model judging: slower and less predictable):

| | Steer before | Check after |
| --- | --- | --- |
| Computational | formatter config, permission lists | tests, type checker, linter, CI |
| Inferential | `AGENTS.md` and the docs it points to | a review pass in a fresh context |

Use the computational row wherever a script can make the call, and keep the inferential row for what needs judgment. Strong types and clear module boundaries make computational checks cheap, which is one more reason your [technical design](/guides/technical-design/) matters.

## What Goes in AGENTS.md

[`AGENTS.md`](https://agents.md/) is an open format for agent instructions: a Markdown file at the repository root that the agent loads at the start of every session. Most coding agents read it, and a tool with its own filename can point that file at it, so write the content once rather than keep two copies that drift apart.

Put in it only what an agent can't find out for itself, because every line costs context on every task. <Cite id="gloaguen-2026" /> found that agents followed context files, but the files didn't significantly change how often they solved a task, raised its cost, and didn't help as repository overviews. <Cite id="dossantos-2026" /> confirmed 58 of 100 popular repositories' files restating rules a linter or formatter already checks. That leaves a short list:

- The commands to install, build, test, and run, exactly as typed.
- Conventions the code doesn't make obvious.
- Constraints, with a pointer to where the reasons live, such as `docs/adr/`.
- Where the work is tracked and what done means (next section).
- Boundaries in three tiers: always, ask first, never.

The tiers come from GitHub's [guidance on writing agent files](https://github.blog/ai-and-ml/github-copilot/how-to-write-a-great-agents-md-lessons-from-over-2500-repositories/). Ask first doubles as the stopping rule: keep working unless a decision needs a person or the next action is on that list. Write the never tier even if you write nothing else, because it's the part that prevents damage, and put security in it, because that's the boundary these files mostly leave out: <Cite id="chatlatanagulchai-2026" /> found security instructions in only 14.8% of the context files they classified, against 75.9% for testing.

For length, use a test rather than a number. [Anthropic's best practices](https://code.claude.com/docs/en/best-practices) ask of each line whether removing it would cause a mistake, and cut it if not. Kept to that test, the file fits on one screen:

```md
# AGENTS.md

## Project
Shift board for <partner>. Requirements: docs/requirements.md.
Architecture: docs/design.md. Decisions and reasons: docs/adr/.

## Commands
npm ci, npm run dev, npm test (Vitest), npm run e2e (Playwright).
npm run check runs types, lint, and tests.

## Work
GitHub Issues; docs/agents/issue-tracker.md says how to read one,
what the labels mean, and how a PR links back. Done means the
issue's acceptance criteria and the Definition of Done in
CONTRIBUTING.md.

## Conventions
- All data access goes through src/server/repos/. No SQL in routes.

## Boundaries
- Always: run npm run check before calling a task done.
- Ask first: adding a dependency; changing the schema, auth, or
  deployment config.
- Never: commit to main, edit a test to make it pass, or paste
  partner data or .env contents into any tool.
```

The last line is your confidentiality rule written for the tools; the version for people belongs in the [working agreement](/guides/working-agreement/#writing-your-agreement).

Some tools also keep a memory, but memory never shows up in a diff, so nobody reviews it: keep it for personal conveniences and put team rules in the file.

## Define Done, Then Let the Agent Check It

An agent stops when the work looks done to it. With no check to run, as Anthropic's best practices put it, "you become the verification loop: every mistake waits for you to notice it." So say what done is before it starts, at three levels:

- The task names its finish line, as the [Generative AI guide](/guides/generative-ai/#start-with-clear-intent) describes. Addy Osmani's [example](https://claude.dev/blog/getting-the-most-out-of-opus-5-5/): every payment endpoint is migrated to the new library, the old one is deleted, and the test suite passes.
- The issue carries acceptance criteria someone could mark passed or failed, written as the [Requirements guide](/guides/requirements/#what-makes-a-good-requirement) shows.
- The project has a [Definition of Done](/guides/sprint/#definition-of-done) that applies to every task, which `AGENTS.md` points to rather than each request repeating.

The criteria live in your issue tracker, which sits outside the repository, so the repository carries the map to it. A short document such as `docs/agents/issue-tracker.md` says how to read an issue, which label marks work ready for an agent, how a pull request links back, and when to file a new issue instead of fixing something in passing. Then "work on the next ready issue" is a complete instruction. GitHub Issues is one example; any board the agent can read works, and if it can't reach yours, paste the criteria into the task.

Criteria become evidence only when the agent can run the checks behind them: one command that brings up a working environment, tests, a type checker, and a linter it runs without you, with error messages that say how to fix the problem. Ask for the test output, not the claim. What to test is the [testing strategy](/guides/testing-strategy/)'s subject.

Don't let the session that did the work be its only reviewer. A reviewer in a fresh context sees only the diff and the criteria, so it doesn't share the author's blind spots. Tell it to report only gaps against correctness and the criteria, because a reviewer asked for problems will find some whether or not they matter.

## Hooks and Gates

Everything in `AGENTS.md` is a request. Anthropic's documentation says so: instruction files are advisory, hooks are deterministic. A **hook** is a script the agent's tool runs on an event, such as before a command or after an edit, whether or not the model paid attention to your instructions. It can refuse a command, format every edited file, or keep the agent from stopping until the tests pass.

Start with the dull checks: no commits to the default branch, no edits to generated files, format after every edit. They block nothing ordinary, which keeps the team from switching them off. Where a list of allowed and denied commands will do, use your tool's permission list instead of a script.

An agent hook is one of three layers, and each catches what the one before it misses:

| Layer | Runs | Bypassed by |
| --- | --- | --- |
| Agent hook | When the agent calls a tool | Working outside that agent |
| Git hook ([`lefthook`](https://github.com/evilmartians/lefthook), [`husky`](https://typicode.github.io/husky/)) | On commit and push | [`git commit --no-verify`](https://git-scm.com/docs/git-commit) |
| CI and branch protection | On the pull request | Anyone on the bypass list |

Anyone can skip a git hook, so the same checks run in CI, where [branch protection](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) turns a red build into a blocked merge. The [workflow](/guides/devops/#continuous-integration-ci) and the [repository settings](/guides/git-and-github/#protecting-the-main-branch), including who can bypass them, are in those guides. A hook answers in milliseconds but stops one agent; CI takes minutes but covers every change. Put fast feedback in the first, and the check you depend on in the last.

## Tools, Data, and Credentials

The [Model Context Protocol](https://modelcontextprotocol.io/) (MCP) is an open standard for connecting an agent to outside services. A server exposes tools the agent can call, such as fetching current library documentation, driving a browser, or reading a database schema. Add one when it answers a question the agent otherwise guesses at, not by default: <Cite id="jain-2025" /> found retrieved documentation improved generated calls to rarely used APIs but, with weak retrieval, hurt calls to common ones.

Treat every server as code running with your credentials. The [MCP specification](https://modelcontextprotocol.io/specification/2026-07-28) states that tools represent arbitrary code execution and that a server's descriptions of its own tools are untrusted unless the server is. Simon Willison [argues](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/) that the dangerous combination is private data, content an attacker controls, and a way to send data out: then a web page or an issue comment can instruct the agent to leak what it reads. Keep the three apart: give a database server read-only access to a development database, keep credentials in environment variables, and keep partner data out of every tool.

## Skills

A **skill** is a packaged set of instructions, optionally with scripts, that the agent loads when a task calls for it; until then only its name and description take up context. The format is an open standard, the [Agent Skills specification](https://agentskills.io/specification). Good candidates are jobs done every week and slightly differently each time, such as a review against the team's conventions or working an issue through to a pull request. Read a published collection, such as Jesse Vincent's [Superpowers](https://github.com/obra/superpowers) or [Matt Pocock's skills](https://github.com/mattpocock/skills), before writing your own, and read any third-party skill before installing it, because it can bundle scripts the agent runs.

A skill and a hook can guard the same mistake, but a skill runs when someone invokes it or the agent judges it relevant, and a hook runs every time. Put a check you'd be sorry to forget in a hook.

## Best Practices for AI Project Setup

- Keep one `AGENTS.md`, and commit the decisions it points to under `docs/`.
- Define done before the agent starts, and make every criterion something a check can confirm.
- Enforce what you explain: `AGENTS.md` says why a boundary exists, and a hook or CI makes it hold.
- Commit instructions, hooks, skills, and tool configuration, so every clone behaves the same.
- Add a line when the agent repeats a mistake, and delete lines that no longer hold, because these files grow by small additions <Cite id="chatlatanagulchai-2026" form="parenthetical" /> and a quarter of them are never touched after they're created <Cite id="dossantos-2026" form="parenthetical" />.
- Trip every check once on purpose, because a check with a typo in its path fails silently.

## Some Truths About AI Project Setup

A team can run agents on a bare repository and ship; the cost arrives later and lands on whoever reviews. <Cite id="denisov-blanch-2026" /> found that among repositories whose first AI tool was an agent, those with no committed AI configuration took on roughly twice the rise in code complexity of those with one, though they caution that teams who write these files may be more disciplined to begin with. And <Cite id="xu-2025" /> found that after Copilot arrived in Microsoft's open-source repositories, core developers reviewed 6.5% more pull requests while their own code output fell 19%.

The evidence that instruction files help is thin and points two ways. <Cite id="gloaguen-2026" /> found no significant change in how often agents solved tasks, at higher cost; <Cite id="lulla-2026" /> found agents finished faster and used fewer output tokens with the file present, but didn't measure whether the work was correct. Neither shows the file making an agent more correct; that comes from the checks.

A check people resent gets switched off, and one nobody has tripped may already be off. Git hooks have `--no-verify`, agent tools have a setting that disables hooks, and a hook that crashes or points at a mistyped path often lets the action through without a word. The team keeps delegating as though the check were there.

A weak criterion gets met literally. "The tests pass" is satisfied by deleting the failing test as surely as by fixing the code, and nothing in that finish line tells the agent to prefer the fix. That's why the example's never tier forbids editing a test to make it pass.

## AI Project Setup in Industry and Academia

The conventions are consolidating in public. OpenAI released `AGENTS.md` and Anthropic released MCP, and both went to the Linux Foundation's [Agentic AI Foundation](https://www.linuxfoundation.org/press/linux-foundation-announces-the-formation-of-the-agentic-ai-foundation) as a neutral home.

The teams building these tools hold their own agents to the same practices. GitHub's cloud agent can't approve or merge its own pull requests, per its [risks and mitigations](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations) page, and OpenAI's Codex team keeps its `AGENTS.md` to [roughly 100 lines](https://openai.com/index/harness-engineering/), used as a map into `docs/`.

In academia the evidence is young: <Cite id="gloaguen-2026" /> tested Python projects only and <Cite id="lulla-2026" /> a single agent, so treat their numbers as a first measurement.
