Sooner or later someone other than you needs to run your system: a new teammate, your project partner, whoever maintains it after you graduate. This page covers which documents to write for each of them, from the README to the API reference, how much detail each one needs, and how to keep them accurate once the code starts moving. It doesn't cover the design document or the requirements, which have guides of their own: [Technical Design](/guides/technical-design/) and [Requirements](/guides/requirements/).

:::note[tl;dr]
- Put a README, a `CONTRIBUTING.md`, and a `LICENSE` at the root of every repository, and test the README by having someone set up the project from it alone.
- Comment why the code does something, not what it does.
- Give every public function a docstring with a short example, and generate the API reference from the docstrings.
- Tag releases with semantic versions and keep a changelog your project partner can read.
- Keep documentation in the repository and change it in the same pull request as the code it describes.
- Delete or fix stale setup steps and code examples first; a stale architecture overview can wait if you mark when it was last checked.
:::

Before writing any of these, decide what each document is for. [Diátaxis](https://diataxis.fr/), a framework by Daniele Procida, sorts documentation by the reader's need into four kinds. A **tutorial** takes a beginner through a first success. A **how-to guide** helps someone who already knows the system finish a specific task. **Reference** describes what exists, precisely and without narrative. **Explanation** covers why things are the way they are. The split matters because the four needs conflict: a tutorial that pauses to justify every design decision loses the beginner, and a reference that tells a story is slow for someone scanning for a function signature. Procida argues that [crossing or blurring the boundaries](https://diataxis.fr/start-here/) between the four is at the heart of a large share of documentation problems. When a page feels wrong and you can't say why, check whether it's trying to be two kinds at once; splitting it in two usually fixes it.

Write for the reader with the least access to you: whoever inherits the project after you leave. That person can't ask you anything, so every gap in the README becomes an afternoon of guessing, and every undocumented decision is at risk of being reversed by someone who didn't know it was a decision. A document that gets that person running also serves the teammate who joins partway through and the project partner who wants to evaluate what you built.

## Repository Documentation

Put a standard set of files at the root of every repository, because that's where GitHub, GitLab, and most other hosts render them, so they're the first thing a visitor sees. Four of them do most of the work: the README, the contributing guide, the license, and the changelog.

### README

The README is the first thing anyone opening your repository reads, so it has to answer the questions they arrive with:

- Purpose: one paragraph on what the project is and the problem it solves.
- Audience: who uses it.
- Setup: step-by-step instructions to install and run it, starting from a clean machine.
- Usage: basic examples with their expected output.
- Status: prototype, in production, actively maintained, or archived.
- Contributing: a link to `CONTRIBUTING.md`.
- License: a link to `LICENSE`.

Test the README the way you'd test code: have someone who hasn't set up the project get it running from the README alone, without asking you, and time it. Somewhere around half an hour is a reasonable target. When it takes much longer, the missing step is usually one the team does from memory, which is exactly the step a newcomer can't guess.

:::tip[README Templates]
[Make a README](https://www.makeareadme.com/) and [Awesome README](https://github.com/matiassingers/awesome-readme) have good examples and templates to start from.
:::

### CONTRIBUTING.md

`CONTRIBUTING.md` tells a new contributor how the team works, in the terms a repository can check. A working agreement records how the team decided to collaborate; this file is its technical side. It should cover:

- Development setup (dependencies, environment variables, local services needed).
- Branching strategy (e.g., feature branches off `main`, naming convention).
- Pull request requirements (required reviewers, review checklist, CI must pass).
- Coding standards (linter, formatter, style guide).
- Definition of Done.
- How to write and run tests.

If the project accepts outside contributions, add a code of conduct next to it, because newcomers read a project's documentation to learn its standards of conduct as well as how to use it. GitHub's Open Source Survey <Cite id="github-2017" form="parenthetical" />, an industry report GitHub designed with researchers from academia and the open-source community, sampled 5,500 respondents at random from over 3,800 open-source repositories. It found that documentation explaining a project's processes, such as contributing guides and codes of conduct, is valued more by groups underrepresented in open source, like women. The [Contributor Covenant](https://www.contributor-covenant.org/) is a ready-made code of conduct you can adopt.

### LICENSE

Add a license or an explicit copyright notice to every repository you share, so anyone who finds it knows what they may do with the code. Without a license, [default copyright law applies](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository): you keep all rights, and no one else may reproduce, distribute, or build on the work. That's rarely what an open-source project intends, and would-be users notice. In the same survey, 64% of respondents called a license very important when deciding whether to use a project, and 67% when deciding whether to contribute to one <Cite id="github-2017" form="parenthetical" />.

Which file you add depends on the project:

- For an open-source project, choose a license.
- For a closed-source project (proprietary, or under an NDA), add a copyright notice.
- For a contribution to an existing open-source project, inherit its license.

The common open-source licenses differ mainly in what they ask of people who reuse the code:

- **MIT**: permissive, with minimal conditions. Pick it when nothing pushes you toward another, because it asks the least of the people who reuse your code.
- **Apache 2.0**: permissive, plus an explicit patent grant from contributors.
- **GPL v3**: copyleft; anyone who distributes a derivative must release it under the same license, so pick it if you want every derivative to stay open.

[Choose a License](https://choosealicense.com/), maintained by GitHub, compares these and the less common ones in plain language.

### CHANGELOG

A changelog records what changed between versions, written for the people who use the software rather than the people who wrote it. Two readers need it most:

- A project partner, who needs to know what to test after each release.
- Users and maintainers of an open-source project, who follow releases closely.

[Keep a Changelog](https://keepachangelog.com/) is a common convention: one section per release, newest first, with entries grouped as Added, Changed, Deprecated, Removed, Fixed, and Security. It argues against pasting the commit log into the changelog, because a commit log is organized by when work happened, while a user needs to know what changed for them. Tag each release with a [semantic version](https://semver.org/) so the changelog's headings match the tags; Versioning, below, covers the scheme.

## Code Documentation

Code documentation lives in the source files, next to what it describes. It carries what the code itself can't: the intent behind it, the assumptions it depends on, and the behavior a caller has to know about.

### Comments: When and How

Comment the *why*, not the *what*. The code already says what it does. A comment earns its place by explaining why it's done this way, what assumption it relies on, or what subtle behavior a reader should watch for. A comment that repeats the code costs a line, and it goes stale the first time someone edits the code without editing the comment.

Good comment:
```python
# Binary search over the sorted segment list.
# Segments are stored as (start, end) tuples; we match by start offset.
```

Unnecessary comment:
```python
i = 0  # initialize i to zero
```

The comment that isn't there is a failure too, and missing information is the most frequent problem with what documentation says. <Cite id="aghajani-2019" /> classified 878 documentation-related artifacts from open-source mailing lists, Stack Overflow, issue trackers, and pull requests. Of the 485 about what the documentation said, 55% reported missing information, and API references and code comments were the documentation types it affected most.

### Docstrings and API Documentation

Give every public function, class, and module a docstring. At minimum, a docstring describes:

- What the function does (not how).
- Parameters and their types.
- Return value.
- Exceptions that may be raised.
- A short example of a call and its result.

Insufficient or inadequate examples were the documentation obstacle developers named most in a survey at Microsoft. <Cite id="robillard-2009" /> asked developers about learning new APIs: 78% of the 80 respondents learned them by reading documentation, and inadequate learning resources topped the list of obstacles, named by 50 of the 74 who reported one. Insufficient or inadequate examples was the most-named of those, by 20 respondents, tied with problems in the API's own structural design as the most-named specific obstacle.

Tools like [JSDoc](https://jsdoc.app/) (JavaScript), [Sphinx](https://www.sphinx-doc.org/en/master/) (Python), [TypeDoc](https://typedoc.org/) (TypeScript), and [Rustdoc](https://doc.rust-lang.org/rustdoc/) (Rust) generate a navigable API reference from the docstrings, so the reference's list of functions and signatures can't fall out of step with the code. The examples inside it still can: <Cite id="aghajani-2019" /> found code examples were the documentation type most often affected by correctness issues, and recommend testing them the way production code is tested. Python's [doctest](https://docs.python.org/3/library/doctest.html) and Rust's [documentation tests](https://doc.rust-lang.org/rustdoc/write-documentation/documentation-tests.html) do exactly that, running the examples in your docstrings as part of the test suite.

For REST APIs, the [OpenAPI Specification](https://spec.openapis.org/oas/latest.html), maintained by the OpenAPI Initiative, is the standard description format. One OpenAPI document can drive rendered documentation, generated client code, and request validation, so you write the description once and get all three from it.

## User Documentation

User documentation explains how to use the software, not how it was built, and its reader is an end user rather than an engineer. For a small project, it might be:

- A user guide or wiki page for each key workflow (a how-to guide, in Diátaxis terms).
- Help text or tooltips in the app.
- A short video walkthrough of a first session (a tutorial).

User documentation matters most when your project partner will hand the software to non-technical users after the team leaves: those users will have questions, and without a guide, the only place to take them is the partner.

## Developer Documentation

Developer documentation targets the people who will build on, maintain, or deploy the system. It includes:

- **Architecture overview**: the major components and how they fit together. Link to your design document.
- **Data model**: the schema and what each entity represents.
- **Environment setup**: how to configure development, test, and production environments.
- **Deployment guide**: how to deploy the system, including environment variables and infrastructure requirements.
- **Troubleshooting guide**: common failure modes and their resolutions.

## Versioning

Use [semantic versioning](https://semver.org/) (`MAJOR.MINOR.PATCH`) for releases:

- **MAJOR**: breaking changes (old integrations may stop working).
- **MINOR**: new features, backward-compatible.
- **PATCH**: bug fixes.

Tag releases in your repository (`git tag v1.0.0`). A tag tells you which version your project partner is running, and gives you a known-good version to roll back to when a release introduces a regression.

## Best Practices

- Write the documentation in the same pull request as the feature, while you still remember the decisions behind it.
- Keep documentation in the repository, next to what it describes, so a reviewer sees the code change and the documentation change in one diff.
- Run the README's setup steps on a fresh machine or in a clean container before each release.
- Fix or delete stale setup steps and code examples as soon as you find them; Some Truths, below, explains why those come first.
- Put a system diagram in the README or the architecture overview, because a newcomer can place a component in a diagram faster than they can reconstruct the system from paragraphs.
- Review documentation in code review, and don't merge a change that adds a public API without its docstring. Some open-source projects make this a rule, adding documentation updates to the contribution checklist or requiring a Javadoc update before a pull request is accepted <Cite id="aghajani-2019" form="parenthetical" />.

## Some Truths About Documentation

Documentation goes stale faster than code, because nothing fails when it's wrong. A broken function breaks a test; a README describing a setup procedure that changed months ago passes every check in your repository and costs the next person an afternoon. <Cite id="lethbridge-2003" /> found that engineers rarely updated documentation other than test documents, and when they did, it was usually several weeks after the code changed; 68% of their survey respondents agreed at least somewhat that documentation is always outdated relative to the system. In open-source projects, outdated information accounted for 39% of the content problems <Cite id="aghajani-2019" /> classified.

The documentation that stayed current in Lethbridge et al.'s studies was tied to work the engineers were already doing. They updated documentation continually only when it was attached to the process for completing a change request, and the documents that stayed accurate were short, needed little effort to maintain, and sat right where the work happened: code comments, notes in the bug tracker, and test cases.

That gives a sharper rule than "keep it updated". Prefer documentation that's executed or generated over documentation that's only written: setup instructions that are a script someone runs can't silently drift, and the same instructions as prose will. Where prose is unavoidable, keep it in the repository next to what it describes and change it in the same pull request, because a document outside the repository isn't in the diff a reviewer reads.

"Outdated documentation is worse than none" is common advice, and the same study suggests it's only half right. Of Lethbridge et al.'s respondents, 81% agreed that documentation can be useful even when it isn't up to date, and the more abstract a document, the more likely engineers were to consider it accurate and useful. How much accuracy mattered depended on how close the document sat to the code: the link between a document's perceived accuracy and how often engineers consulted it was strongest for test documents and low-level design, weaker for requirements and architecture, and near zero for specifications.

Use that split to decide what to fix first. Wrong information concentrates in the documentation a reader executes: of the correctness issues <Cite id="aghajani-2019" /> could attribute to a documentation type, 50% were in code examples and 20% in installation guidelines. Fix or delete a stale setup step or code example as soon as you find it, because a reader follows it exactly and has no way to tell it's wrong until it fails. A stale architecture overview still orients a newcomer if its major components are right, so mark when it was last checked instead of deleting it. Google does this at scale: <Cite id="manshreck-2020" /> describes documents that carry an owner and a "last reviewed" date, with a reminder sent when one hasn't been reviewed in a few months.

Writing documentation rarely pays off for the person writing it. Manshreck gives a structural reason: the benefits of documentation arrive downstream, for its readers, while the cost lands up front, on its author. Resolve doesn't fix that; making the moment specific does. Attach documentation to something you already do, such as the pull request that adds a feature or the review that looks over your `docs/` directory, so the question is never "should I write documentation today" but "does this change alter anything a reader was told".

## Documentation in Industry and Academia

Google's own history is a case study in how documentation goes stale. In Manshreck's account, the company's internal wiki, which anyone could edit and nobody owned, filled with obsolete and duplicated pages: at one point there were 7 to 10 documents on setting up Borg, Google's production compute environment, only a few of them maintained. Documentation quality became the number one developer complaint on Google's annual developer surveys, and when the wiki was retired, around 90% of its documents had had no views or updates in the previous few months. The fix was to treat documentation like code, with owners, canonical locations in source control, bug tracking, and code review, and Manshreck reports that the documents became better.

Technical writers don't take documentation off an engineer's plate. Manshreck notes that engineers will always write most documentation themselves, and that at Google most of it takes the form of code comments. Treat your project's documentation as practice for that part of the job, and for the writing a senior engineering role adds to it, because much of that role's influence runs through writing: design documents, incident reports, proposals, and review comments that change someone's mind.

Open-source projects show the same pattern. In GitHub's survey, 93% of respondents had run into incomplete or outdated documentation, yet 60% of contributors said they rarely or never contribute to documentation <Cite id="github-2017" form="parenthetical" />. The report's recommendation to its readers follows from those two numbers: when you hit a documentation problem in someone else's project, open a pull request that fixes it.

In research, the benchmark is reproducibility: another researcher should be able to run your code and reproduce your results from your documentation alone. Borrow that test for any project you hand over, because it's concrete where "well documented" isn't: it names a reader (someone who wasn't on the team), a starting point (a clean checkout), and an expected result (the system running and producing what yours does).
