Your team has one repository, four people who can push to it, and a demo coming up. Sooner or later two of you edit the same file on the same afternoon, or someone pushes a broken build straight to `main` the night before that demo. This page covers the way of working that prevents both: a branching workflow, the pull request cycle from branch to merge, merge conflicts, and the repository settings that enforce the workflow. It doesn't teach Git from scratch (the two lectures linked below do), and it doesn't cover writing a CI pipeline, which is in the [DevOps guide](/guides/devops/).

:::note[tl;dr]
- Use GitHub Flow: `main` stays deployable, and every change reaches it through a pull request from a short-lived branch.
- Keep branches to a day or two, and keep each pull request small enough for a teammate to read in one sitting.
- Write commit messages and pull request descriptions that say why the change was made; the diff already shows what.
- Protect `main` with a ruleset: require a pull request, require CI to pass, block force pushes, and leave the bypass list empty.
- Squash and merge, then delete the branch.
- When something goes wrong locally, stop and read `git reflog` before improvising; almost every committed state is recoverable.
- Never commit a secret. If one slips in, rotate it first and clean the history second.
:::

[Git](https://git-scm.com/) is a distributed version control system: every clone holds the project's full history as a graph of commits, and a branch is a movable label that points at one of them. [GitHub](https://github.com/) hosts Git repositories and adds the collaboration layer on top: pull requests, code review, issues, and the settings that control who can change what. If you're new to either, or need a refresher, start with these two lectures and come back.

## Branching Workflows

A branching workflow is the team's agreement on when to create a branch, how a change gets reviewed, and how it reaches `main`. Without one, teammates build on different ideas of which branch is current, `main` breaks, and nobody trusts that what they just pulled will run. Three workflows are common. They differ in how much structure they add and in how much they lean on automated tests.

### GitHub Flow

[GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow) has one rule: `main` is always deployable, or at least stable. All work happens on short-lived branches that return to `main` through a pull request, where a teammate reviews the change and CI runs the tests before it merges.

Use GitHub Flow on a small team shipping one product. It's simple enough that everyone will actually follow it, and it still enforces the two practices that matter most on a small team: working on branches, and reviewing each other's code before it merges.

### Git Flow

[Git Flow](https://nvie.com/posts/a-successful-git-branching-model/), described by Vincent Driessen, keeps a long-lived `develop` branch next to `main`, plus dedicated branches for releases and hotfixes. It gives structure to projects with formal release cycles, at the cost of more branches to keep in sync. Driessen later added a note to the post that narrows its scope: for software delivered continuously, such as most web apps, he suggests a simpler workflow like GitHub Flow, and he keeps Git Flow for software that is explicitly versioned or that has several versions in use at once. A library whose users pin old versions fits the second case; a web app deployed from `main` fits the first.

### Trunk-Based Development

In [trunk-based development](https://trunkbaseddevelopment.com/), everyone commits to `main` (the "trunk"), either directly or through branches that live for hours. Google works this way at scale. <Cite id="potvin-2016" /> describe a single repository where most engineers work at the latest version, development on branches is unusual, branches exist mainly for releases, and new features sit behind configuration flags instead of on long-lived branches. It holds together because of what surrounds it: every change is tested before it lands, affected code is rebuilt on almost every commit, and a change that breaks the build widely is rolled back automatically.

Industry data on branch lifetime points the same way. The 2017 State of DevOps Report, an industry report by Puppet and DORA based on a survey of practitioners, restates the previous year's findings that merging into trunk daily, keeping branches alive for less than a day, and having fewer than three active branches all contributed to higher software delivery performance, and confirms them with new data: high performers' branches typically lived for hours where low performers' lived for days <Cite id="forsgren-2017" form="parenthetical" />. The report takes up the objection from developers used to the GitHub-recommended workflow and answers it: short-lived branches merged into trunk at least daily are consistent with continuous integration. The two workflows are closer than they look. GitHub Flow with branches that last a day is nearly trunk-based development; GitHub Flow with branches that last for days is the pattern the report found among low performers.

:::tip[Which Workflow to Pick]
Start with GitHub Flow and keep branches to a day or two. Move toward trunk-based development once your CI catches real regressions and the team trusts a green build; without that suite, committing straight to `main` means shipping untested code. Reach for Git Flow only if you ship versioned releases that you support side by side.
:::

## GitHub Flow in Practice

This section walks through GitHub Flow one step at a time, from creating a branch to merging a pull request, with the commands for each step.

### 1. Start from an up-to-date main branch

Before starting new work, update your local `main` to match the remote repository, so you build on what your teammates already merged rather than on last week's code.

```bash
git checkout main
git pull origin main
```

### 2. Create a feature branch

Create a branch for the piece of work you're about to do. Name it so a teammate can tell what it holds from the branch list alone, following whatever convention your team wrote into its [working agreement](/guides/working-agreement/).

```bash
git checkout -b feature/add-login-endpoint
```

Common naming conventions:

- `feature/add-login-endpoint` for new functionality
- `fix/null-pointer-dashboard` for bug fixes
- `chore/update-dependencies` for maintenance tasks

If the work corresponds to a GitHub issue, put the issue number in the branch name, so anyone can trace the branch back to the discussion that motivated it:

```bash
git checkout -b feature/42-add-login-endpoint
```

Each branch holds one focused change. A branch called `feature/add-login-endpoint` that also refactors the database layer and updates the README makes the reviewer untangle three changes to approve one, and none of the three can be reverted without losing the other two.

### 3. Make commits as you work

Commit in logical increments: each commit a coherent step that makes sense on its own. That's not every save, and it's not a whole feature in one commit either.

```bash
git add src/auth/login.py src/auth/tests/test_login.py
git commit -m "Add login endpoint with email/password validation"
```

A commit message has a subject line that says what changed and, when the change needs it, a body that says why. Chris Beams argues for [seven rules](https://cbea.ms/git-commit/), among them a subject of about 50 characters written in the imperative ("Add", not "Added") and a body that explains what and why rather than how. Treat the body as the part that matters, because the diff already shows what changed, and the reason is the one thing a reader six months later can't reconstruct from the code.

If your team wants machine-readable history, [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) adds a `type(scope): subject` prefix, such as `feat(auth): add login endpoint`, that tools parse to generate changelogs and pick the next version number. It costs a little discipline on every commit and pays off only if you run those tools, so adopt it if you plan to automate releases and skip it if you don't.

Good commit subjects:

```
Add login endpoint with email/password validation
Fix token expiration check to use UTC consistently
Add integration tests for login with invalid credentials
```

A good commit with a body:

```
Fix token expiration check to use UTC consistently

The check compared the token's UTC timestamp with the server's local
time, so on a server set to Pacific time, tokens stayed valid for hours
after they had expired.
```

Poor commit messages:

```
WIP
fix stuff
update files
```

### 4. Push your branch to GitHub

Push your branch so teammates can see your work and so it's backed up. Until you push, the only copy of that work is on one laptop, and nothing else on this page can recover it.

```bash
git push origin feature/add-login-endpoint
```

The first time you push a branch, add the `-u` flag to set up tracking between your local branch and the remote one:

```bash
git push -u origin feature/add-login-endpoint
```

After that first push, `git push` on its own is enough.

### 5. Open a pull request

On GitHub, open a pull request (PR) from your branch into `main`. The PR is where a teammate reviews the change and CI runs against it before anything merges.

A good pull request has:

- A title that says what the change does: "Add login endpoint with email/password validation".
- A description that says what changed, why, and how to test it. If the PR resolves an issue, write `Closes #42` in the description, and GitHub [closes the issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue) when the PR merges into the default branch.
- A size a reviewer can read in one sitting. If it's growing past that, split it into smaller PRs that merge in sequence.

The description and the size both serve the reviewer's understanding, which is where review struggles most. In interviews with Microsoft developers, <Cite id="bacchelli-2013" /> found that understanding the change, and in particular the reason for it, was reviewers' main challenge, and developers said that when the author gave them context and direction, they could respond better and faster. Keep your pull requests small, because a reviewer who can hold the whole change in their head can check it, and one who can't has to skim. Google's process has converged on small changes: <Cite id="sadowski-2018" /> report a median of 24 lines changed per change, about 90% of changes touching fewer than 10 files, and a median of under four hours for the whole review.

:::tip[Draft Pull Requests]
If your work isn't ready for review but you want early feedback, or want teammates to see where you are, open a [draft pull request](https://docs.github.com/en/pull-requests/reference/pull-requests). A draft can't be merged and doesn't request reviews automatically. Mark it ready for review when it is.
:::

### 6. Review and discuss

At least one teammate, or however many your working agreement names, reviews the pull request. A reviewer checks:

- Does the code do what the PR description says it does?
- Is the code readable and consistent with the project's style?
- Are there tests, and do they cover the important cases?
- Does the change introduce obvious bugs, security issues, or performance problems?

Reviewers comment on specific lines or on the PR as a whole. The author responds, makes changes where needed, and pushes more commits to the same branch, and the PR updates automatically.

```bash
# After addressing review feedback
git add src/auth/login.py
git commit -m "Handle empty password field per review feedback"
git push
```

Most people expect review to catch bugs. It catches some, but that's not most of what it produces. In the same Microsoft study, finding defects was the top motivation developers and managers gave for reviewing, yet of 570 review comments only 78 (14%) were about defects, the fourth most common of nine categories, while 165 (29%) were code improvements such as better practices, removing unused code, and readability <Cite id="bacchelli-2013" form="parenthetical" />. The authors found that review also produces knowledge transfer, team awareness, and alternative solutions to problems. They also recommend spreading understanding of the code across the team, because when the author of a change is the only person who knows that code, nobody else is in a position to review it.

That doesn't make review optional for quality. <Cite id="mcintosh-2014" /> studied review participation in two open-source projects, Qt and ITK, and found that components integrating more changes merged without any review discussion had more post-release defects in all three releases they modeled. Self-approved and hastily reviewed changes showed the same effect in one Qt release each.

### 7. Merge into main

Once the PR is approved and the CI checks pass, merge the branch into `main`. GitHub offers [three merge methods](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github):

- **Merge commit**: keeps every commit from the branch in `main`'s history, plus a merge commit that joins them.
- **Squash and merge**: combines all the branch's commits into a single commit on `main`.
- **Rebase and merge**: replays the branch's commits on top of `main` without a merge commit, for a linear history.

Make squash and merge your default, because it keeps `main` readable as one commit per pull request while letting you commit freely on the branch, "fix typo" and "WIP" included. The cost is that the branch's individual commits and their timestamps don't reach `main`, so the squashed commit's message, which GitHub lets you edit when you merge, has to carry whatever a later reader needs.

After merging, delete the branch. GitHub can [do this automatically](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-the-automatic-deletion-of-branches). Don't keep working on a branch after it's been squashed and merged: its old commits reappear in the next pull request from it, and you'll resolve the same conflicts again.

### 8. Pull the updated main branch

After a merge, everyone else pulls the latest `main` before starting new work:

```bash
git checkout main
git pull origin main
```

If you have a branch in progress, bring it up to date with `main`, so it doesn't drift far enough to make the eventual merge painful:

```bash
git checkout feature/your-branch
git merge main
```

Because squash and merge creates a new commit on `main`, `git branch --merged` won't list your old local branch as merged. Once GitHub shows the PR as merged, delete the local branch with `git branch -D feature/your-branch`.

## Handling Merge Conflicts

A merge conflict happens when two branches change the same lines of the same file, and Git can't decide which version to keep, so it stops and asks you (Pro Git covers the mechanics in [Basic Merge Conflicts](https://git-scm.com/book/en/v2/Git-Branching-Basic-Branching-and-Merging)). The first one feels alarming because your files now contain markers that aren't valid code. Git's message, "Automatic merge failed; fix conflicts and then commit the result.", tells you what to do next but not that you can back out: `git merge --abort` returns you to where you started.

When a conflict occurs, either during `git merge` or when GitHub can't merge a PR on its own, Git marks the conflicting sections in the file:

```
<<<<<<< HEAD
def authenticate(email, password):
    return check_credentials(email, password)
=======
def authenticate(user_email, user_password):
    return verify_user(user_email, user_password)
>>>>>>> feature/refactor-auth
```

To resolve it, edit the file to keep the correct version (or combine both), delete the markers, then stage and commit:

```bash
git add src/auth/login.py
git commit -m "Resolve merge conflict in authenticate function"
```

The longer two branches live apart, the more lines both of them touch, so conflicts grow with branch lifetime. If your team keeps hitting painful conflicts, fix them with smaller, more frequent pull requests and a quick word with whoever works in the same area of the code, because that shrinks the overlap itself, where better resolution skills only make each collision cheaper.

If you find yourself resolving the same conflict on every rebase, turn on [`git rerere`](https://git-scm.com/docs/git-rerere) ("reuse recorded resolution") with `git config --global rerere.enabled true`. Git then records how you resolved a conflict and replays that resolution the next time the same one appears.

## Protecting the Main Branch

Everything above depends on people remembering to follow it, and GitHub can enforce it instead. A [ruleset](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets) is a named list of rules that GitHub applies to matching branches on every push and merge. Rulesets are the newer mechanism and work alongside classic branch protection rules. Prefer them on a new repository, because several rulesets can apply to one branch at once, you can switch one off without deleting it, and anyone with read access can see which rules are active.

Both rulesets and classic protection are available on public repositories under GitHub Free, but on private repositories only with a paid plan such as GitHub Pro or GitHub Team. If your repository is private and owned by a free organization, check the plan before you rely on these settings.

For a small team, these rules are worth turning on (the full list is in [Available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)):

- "Require a pull request before merging", with at least one required approval, so nothing reaches `main` without review.
- "Require status checks to pass before merging", so CI has to be green before the merge button works.
- "Block force pushes", which is on by default and stops anyone rewriting `main`'s history under their teammates.
- An empty bypass list. A ruleset applies to everyone who isn't on that list, and on a small team's repository everyone usually has admin access, so any role you add there exempts the whole team.

To create one, open the repository's Settings, choose Rulesets in the left sidebar under "Code and automation", and click New ruleset, then New branch ruleset. Target the default branch, and change the enforcement status from Disabled, the default for a new ruleset, to Active.

If the repository already has a classic branch protection rule, it behaves differently on one point: [by default](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) its restrictions don't apply to administrators. Turn on "Do not allow bypassing the above settings", or convert the rule to a ruleset.

## Best Practices

- Commit early and often. Small commits are easier to review and to revert, and a commit is the only kind of work `git reflog` can bring back.
- Pull `main` before starting new work, so you build on what your teammates have already merged.
- Keep branches short-lived: a day or two at most. The State of DevOps findings above put high performers' branches at hours, and a branch that lives for two weeks piles up conflicts.
- Write the why into commit messages and pull request descriptions.
- Never commit secrets. API keys, passwords, and tokens belong in environment variables, and the files that hold them belong in `.gitignore`.
- Set up `.gitignore` before the first commit, starting from GitHub's [templates](https://github.com/github/gitignore) for your language and framework, so build artifacts, IDE settings, and OS files never enter the history.

### A History a Maintainer Could Inherit

The habits above are for you. These five are for whoever takes the repository over after you, and each one is cheap now and expensive to fix later:

- Nothing lands on the default branch except through a pull request, enforced by the ruleset above.
- No secrets, build artifacts, or dependency directories in the history. A committed `.env` stays in the history after you delete the file; GitHub's guidance on [removing sensitive data](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository) is to revoke or rotate the secret first and rewrite the history second.
- Commit messages say what changed and why, with noisy branches squashed on merge.
- Nobody force-pushes the default branch.
- Large binaries stay out of Git, or go in [Git LFS](https://git-lfs.com/), because every clone downloads every version of every file ever committed.

## Some Truths About Git

Git is hard to learn, and if you find it confusing, the problem is partly Git's. <Cite id="perezderosso-2013" /> observe that Git puzzles even experienced developers, and they trace much of the difficulty to its concepts rather than its commands. A "tracked" file and a "staged" file sound interchangeable and aren't: edit a file after `git add` and a plain `git commit` records the version you added, not the one on disk. The fastest way through is to learn the model (a graph of commits, with branches as movable labels pointing into it) before memorizing commands, which is what the first three chapters of [Pro Git](https://git-scm.com/book/en/v2) teach. After that, most commands follow from the model and the rest are lookups.

Almost every mistake you can make locally with committed work is recoverable, which is worth knowing before the first time you panic. [`git reflog`](https://git-scm.com/docs/git-reflog) records every commit `HEAD` has pointed at, including commits no branch points at anymore, so a bad reset, a deleted branch, or a botched rebase is usually one `git reset --hard HEAD@{n}` away from undone (run it on a clean working tree, since `--hard` discards uncommitted changes). Two limits apply. Work you never committed isn't in the reflog, which is why committing often is about safety as much as tidiness. And reflog entries expire, by default after 90 days, or 30 for commits no branch can reach ([`git gc`](https://git-scm.com/docs/git-gc)). When something goes wrong, stop, read the error message, and look at the reflog before trying fixes, because a string of improvised fixes is what turns a recoverable mistake into a lost afternoon.

Skipping code review saves time this week, and review costs the author time, so a review that takes days is the kind a team starts skipping. Google's published [code review guidelines](https://google.github.io/eng-practices/review/) are built to keep that cost down. Their [central standard](https://google.github.io/eng-practices/review/reviewer/standard.html) is to approve a change once it definitely improves the overall health of the code, even if it isn't perfect, rather than holding out for the version the reviewer would have written. Their page on [review speed](https://google.github.io/eng-practices/review/reviewer/speed.html) argues that slow reviews make developers protest the process and that most of those complaints go away once reviews get faster, and it sets one business day as the longest a review request should wait. Adopt both as written, because together they keep review from stalling on taste or on a review request nobody has opened.

Which workflow you choose matters less than whether everyone follows it. All three workflows above work for the teams they were designed for. What doesn't work is a mix: two people open pull requests, one pushes straight to `main`, and nobody is sure which branch is current. Pick GitHub Flow, write it into the [working agreement](/guides/working-agreement/), and enforce it with a ruleset, because a rule the repository enforces doesn't depend on anyone remembering it at midnight.

No set of rules fits every change. A one-character typo fix in the README doesn't need the same scrutiny as a new authentication flow, and a team that makes the typo fix as slow to merge as the feature gives everyone a reason to batch unrelated changes into bigger pull requests, which are harder to review. Keep the protections on and make the small case cheap instead: a teammate can read and approve a typo fix in a minute.

## Git and GitHub in Industry and Academia

Git is the default in industry. The 2022 Stack Overflow Developer Survey, an industry report, found that 94% of the roughly 71,000 respondents who answered its version control question used Git and 5% used SVN, and GitHub was the most used host for both personal and professional work, with GitLab, Bitbucket, and Azure Repos more common at work than for personal projects <Cite id="stackoverflow-2022" form="parenthetical" />. The respondents were recruited mostly through Stack Overflow's own site, so the sample leans toward its most active users, but the gap between Git and everything else is too large for that to change the ranking.

Large companies use the same building blocks, arranged differently. Google skips feature branches for the trunk-based development described above, but not review: review has been required there since early in the company's history, and the median change has a single reviewer <Cite id="sadowski-2018" form="parenthetical" />. At Microsoft, the teams in one study reviewed code through an internal tool that more than 40,000 developers had used <Cite id="bacchelli-2013" form="parenthetical" />.

In open source, the pull request is how outsiders contribute: you fork the repository, push a branch to your fork, and open a pull request against the original, where the maintainers review it ([Contributing to a project](https://docs.github.com/en/get-started/exploring-projects-on-github/contributing-to-a-project), GitHub). That's the flow on this page with a fork added, so practicing it on your own team is also how you learn to contribute to a project you don't control.

In research, <Cite id="ram-2013" /> argues for Git as a tool for reproducible science. He notes that sharing the data and code behind a publication is becoming more common, driven partly by journal requirements and funder mandates, while access to them is still uncommon, and argues that a Git history keeps a complete provenance of a project's data. He also warns that a hosting service isn't an archive, since none guarantee permanence, and recommends depositing a snapshot in an archival repository. GitHub documents how to [archive a repository in Zenodo](https://docs.github.com/en/repositories/archiving-a-github-repository/referencing-and-citing-content) and get a DOI you can cite.
