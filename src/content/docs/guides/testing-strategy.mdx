Your team has code merging every week, some of it written by AI tools, and a project partner who will judge the result by whether it does what they need. This page covers what to test automatically and in what proportion, how to keep the suite trustworthy, and how to check with real users that you're building the right thing. It doesn't cover the CI workflow file (see [DevOps](/guides/devops/)), branch protection (see [Git and GitHub](/guides/git-and-github/)), or accessibility testing (see [Accessibility](/guides/accessibility/)).

:::note[tl;dr]
- Test first the paths where a failure would cost the most (authentication, payments, the core data flow), not the code that's easiest to test.
- Run the suite in CI on every pull request and block the merge when it's red.
- Test behavior rather than implementation, and start at the boundaries: empty input, maximum values, invalid data.
- Use coverage to find code no test runs, never as a target: it correlates only weakly to moderately with whether a suite catches faults.
- Quarantine a flaky test the day it appears, then find the cause before you delete it; some flaky tests are reporting a real bug.
- Put the product in front of real users in planned sessions of a few people each, and run several small rounds rather than one large one.
- In research code, validate the input data and sanity-check the outputs; treat a sudden near-perfect score as leakage until you've ruled it out.
:::

Testing answers two questions. **Verification** asks whether the code does what you specified: unit tests, integration tests, CI, exploratory testing. **Validation** asks whether what you specified solves the user's problem: usability sessions, beta feedback, experiments, and demos to the people who'll use the product.

## Thinking About Your Testing Strategy

Decide what confidence your project needs before choosing a framework, because a data pipeline and a public web app need different tests. Four questions settle most of it:

- Who uses it, and when do they first touch it? Software handed to non-technical users after the team leaves needs usability testing. A pipeline whose only user is a data scientist needs reproducibility checks.
- Where would a failure be most expensive? A payment flow or an authentication path earns rigorous automated tests; an about page doesn't. A model pipeline earns validation against a known baseline.
- When will real users see it? Put user sessions on the board in the sprint you intend to run them, because work that isn't on the board has no owner and no time set aside for it.
- What does your [Definition of Done](/activities/planning/#definition-of-done) already promise? If it requires green tests in CI (continuous integration), you need the pipeline before you need more kinds of test. If it requires sign-off from the project partner, you need a demo and a feedback loop.

Write the answers into your [working agreement](/guides/working-agreement/) or `CONTRIBUTING.md` in a few lines: which kinds of testing the team does, when automated tests are required, and when users are involved.

## Testing as Part of Your Checks

Your **checks** are everything that catches a bad change before it reaches a user:

- tests that fail when behavior breaks, on the paths that matter;
- CI on every pull request, required to pass before merge;
- review gates on the hard-to-reverse decisions (schema, authentication, deployment, data migrations);
- a staging or preview environment, so the first run of a change isn't in production;
- a rollback path you've actually tried.

Delegate to AI tools only as far as those checks would catch a mistake, and strengthen the checks before you delegate more, because a tool's output can look right and still be wrong in ways nobody reads closely enough to see. The [Generative AI guide](/guides/generative-ai/#verify-what-matters-and-build-the-checks-that-let-you-trust-the-rest) makes that argument in full, and [Audit Your Safety Net](/activities/ai/#audit-your-safety-net) measures the gap on your own repository. Tests are the part of the checks this page covers.

## Verification: Does the Code Work?

Verification covers automated tests, which run without anyone watching, and manual checks, which need a person using the system.

### Automated Testing

Automated tests are code that exercises your code. They run in seconds or minutes, give the same answer every time they run (when they're written well), and catch a regression before a user does.

#### Unit Tests

A unit test checks one function, method, or component in isolation. It's fast, cheap to write, and when it fails it points at the line that broke.

```python
def test_calculate_total_with_discount():
    result = calculate_total(price=100, discount=0.2)
    assert result == 80.0
```

Write unit tests for business logic, data transformations, and utility functions, where the inputs and outputs are well defined.

#### Integration Tests

An integration test checks that several components work together: a function that queries a database, an API endpoint that authenticates a user and returns data, a pipeline that reads from one source and writes to another.

```python
def test_create_user_stores_in_database(db_session):
    response = client.post("/users", json={"email": "test@example.com"})
    assert response.status_code == 201
    assert db_session.query(User).filter_by(email="test@example.com").one()
```

Integration tests are slower than unit tests, but they catch what a unit test can't see: a configuration error, a schema mismatch, a wrong assumption about how a library or service behaves.

#### End-to-End Tests

An end-to-end (E2E) test checks the system the way a user meets it: open a browser, click through a workflow, and assert that the expected result appears. For a web application, that might mean logging in, creating a resource, and finding it on a dashboard. For a data pipeline, it means feeding raw data in and checking the final output.

E2E tests are the slowest and the most likely to break for reasons unrelated to your change, but they catch failures no other test reaches: broken routing, a missing environment variable, a UI element that never renders, a workflow that breaks across a service boundary.

#### Contract Tests

When a frontend consumes a backend API, a contract test checks that both sides agree on the shape of requests and responses, so a breaking change fails at the interface instead of at runtime. If different teammates own the two sides, even a light version (validating API responses against an [OpenAPI](https://spec.openapis.org/oas/latest.html) schema) catches the mismatch before it reaches a demo.

#### The Testing Pyramid

The **testing pyramid** is a model for balancing these types: many fast, focused unit tests at the base, fewer integration tests in the middle, and a few slow, broad E2E tests at the top. [Fowler traces it](https://martinfowler.com/bliki/TestPyramid.html) to Mike Cohn, who described it as the "Test Automation Pyramid" in *Succeeding with Agile* (2009).

```
    /   E2E   \        Few, slow, broad
   /───────────\
  / Integration \      Some, moderate speed
 /───────────────\
/   Unit Tests    \    Many, fast, focused
```

The pyramid is one of two competing models. Fowler notes that it rests on the assumption that broad tests are slow, expensive, and brittle, and that if your high-level tests are fast, reliable, and cheap to change, lower-level tests aren't needed. Kent C. Dodds's [testing trophy](https://kentcdodds.com/blog/static-vs-unit-vs-integration-vs-e2e-tests) argues for more integration tests than unit tests, on the grounds that the more a test resembles the way the software is used, the more confidence it gives, and that a unit test can't tell you whether you're calling a dependency correctly. Mike Wacker, on Google's Testing Blog, argues from the other end that you should [say no to more end-to-end tests](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html), because they give slow, flaky feedback and a failure is hard to trace to the code that caused it. Which shape fits depends on how expensive your integration tests actually are, so measure that before you commit to a shape.

#### What to Test

Spend tests where a failure would hurt, not where tests are easiest to write:

- Test behavior, not implementation. A test that asserts "the output is sorted" survives a refactor; one that asserts "the function calls `sort()` internally" breaks every time the code changes, even when the behavior hasn't.
- Cover the critical paths thoroughly: authentication, payment processing, the core data pipeline, the primary user interaction. Edge cases in a settings page can wait.
- Test the boundaries first (empty inputs, maximum values, invalid data, concurrent access), because a boundary is where a single wrong comparison flips the result, and it's the case a happy-path test never reaches. If a function accepts a list, test it with an empty list, one item, and a very large list.
- Don't test framework code. If the framework guarantees a 404 for an unregistered route, test your code instead of theirs.
- Don't chase a coverage number. Use coverage to find code no test executes; Some Truths below explains why a target backfires.

### Manual and Exploratory Testing

Automated tests check what the team told them to check. A person using the system notices what nobody thought to write a test for: a button that works but is invisible on a dark background, a form that submits successfully and confuses every user, a workflow that's technically correct and takes twelve clicks instead of two.

**Exploratory testing** is unscripted manual testing: someone uses the system without a checklist, looking for anything that feels wrong, such as a confusing workflow, an unexpected state, a visual glitch, or a slow page. Run it after a major feature is complete and before a demo or release, when there's a whole workflow to explore.

**Smoke testing** is a quick manual check that the most critical workflows still function after a deployment or a significant change. It answers one question, whether the system is broken outright, before anyone spends time on more detailed verification.

## Validation: Does the Product Solve the Right Problem?

Validation confirms that the system is worth building in its current form, which only the people it's built for can tell you. It puts the product in front of real users and asks whether it works for them.

### Usability Testing

Watch real users, or reasonable proxies, attempt key tasks in your system, and note where they hesitate, make mistakes, or say they're confused. Keep each round small and run several: <Cite id="nielsen-1993" /> modeled problem discovery across 11 studies and, for their medium example, estimated the best benefit-to-cost ratio at four evaluations. Nielsen later [argued for about five users per round](https://www.nngroup.com/articles/why-you-only-need-to-test-with-5-users/), because each added user reveals less that's new and the budget is better spent testing the redesign.

Test before the product is finished. Paper prototypes, clickable mockups, and half-built features are all testable, and a problem found in a mockup costs a redraw instead of a rewrite.

Plan each session: pick the tasks to test, recruit the participants, and write a script. "Try it and tell me what you think" gets opinions; "book a room for Thursday" shows you where the user gets stuck.

### Testing with Assistive Technology Users

Only someone who relies on assistive technology daily can tell you whether the software is good rather than merely compliant. [Accessibility Testing](/guides/accessibility/#testing-with-assistive-technology-users) covers how to recruit for that session and what the closest substitute is when you can't.

### Beta Testing and Feedback

A beta gives a working version of the software to a small group of users and collects structured feedback on how it behaves in their real conditions. Decide what you want to learn before you distribute it, and ask specific questions tied to your acceptance criteria, because "let us know what you think" gets general impressions you can't act on.

### A/B Testing and Experiments

When success is measurable (conversion rates, task completion times, error rates), an [A/B test](https://experimentguide.com/) shows two variations to different users and compares the outcome. It needs enough users for the difference to be statistically meaningful, which a product with a few dozen users can't reach. The reasoning behind it still applies at any size: state a hypothesis, measure the outcome, and decide on the evidence.

### Project Partner Demos as Validation

Treat every sprint demo as a test of whether you built the right thing. When the project partner watches a feature and says "that's not what I meant", you've found a requirements bug, and a demo finds it within a sprint of the code being written instead of at the end of the project. The [Presentations guide](/guides/presentations/) covers how to run a demo that gets that feedback.

:::note[IRB Approval]
If your project is part of a research study and you plan to test with human participants, you may need [IRB (institutional review board) approval](https://research.oregonstate.edu/ori/irb). Ask your faculty advisor early, because review takes weeks you don't control.
:::

## Testing Research Projects

In a research project, the question a test answers is whether the results are reproducible and trustworthy. The [Shipping guide](/guides/shipping/#research) covers what reproducible means and why you reproduce the baseline before attempting anything new. Two checks are testing work:

- Validate the input data. Check that it meets the expected formats, ranges, and distributions before processing, because a pipeline that silently drops malformed records or produces NaN without warning produces results nobody can trust.
- Sanity-check the outputs. After a model trains or an analysis runs, verify that the outputs fall in the expected range. Treat a model that suddenly reports 99.9% accuracy as a data-leakage bug until you've ruled it out, because test data leaking into training makes a model look far better than it is.

Research output that others will use (a tool, a dataset, a method) needs validation as well: put it in front of the intended audience and watch whether it works for them.

## When to Test

Testing runs through the whole workflow:

- As you build. Tests exist before the code merges, whether the team writes them first or alongside, because a change merged without them can break later without anyone noticing.
- On every pull request. Tests run in CI and a red build blocks the merge, which makes the suite a gate instead of a suggestion. The workflow file is in the [DevOps guide](/guides/devops/#continuous-integration-ci); the branch protection that makes red mean blocked is in [Git and GitHub](/guides/git-and-github/#protecting-the-main-branch).
- In the sprint you planned it. User testing appears on the board as work with an owner.
- Before every demo and release. Run the full suite plus a manual smoke test. If a workflow matters enough to demo, give it an end-to-end test.
- After every bug that reaches a user. Write a test that reproduces the failure before you fix it, so the test proves the fix and keeps the bug from coming back ([Fowler](https://martinfowler.com/bliki/TestPyramid.html) advises a unit test even when an end-to-end test found the bug). Over the project, that builds a suite shaped by real failures rather than imagined ones.

## Organizing and Maintaining Your Test Suite

Organize tests so any teammate can find, run, and change them:

- Keep tests close to the code they test: a `tests/` directory mirroring the source tree, or colocated files (`login.test.ts` next to `login.ts`). Either works; pick one and use it everywhere.
- Name tests descriptively. `test_login_with_invalid_password_returns_401` tells a reviewer what's verified without reading the body.
- Build test data with fixtures, factories, or builders rather than hardcoding it in each file, so a schema change means one edit instead of forty.

Write the conventions (framework, file layout, how to run the suite) into `CONTRIBUTING.md`, so every teammate and every AI coding tool follows the same pattern. The [Documentation guide](/guides/documentation/) covers what else belongs there.

### Dealing with Flaky Tests

A **flaky test** passes and fails on the same code. <Cite id="luo-2014" /> studied 201 commits that likely fixed flaky tests in 51 open-source Apache projects and classified the cause of 161: 45% were async waits, 20% concurrency, and 12% test order dependency, 77% together. Each of those has a fix, below, along with the one for tests that depend on the network, the clock, or random numbers:

- **Async wait**: the test uses a result before an asynchronous call has produced it, sometimes hidden behind a `sleep()`. Wait explicitly for the condition instead.
- **Concurrency**: threads interleave differently on different runs. Add the missing synchronization or make the code deterministic.
- **Test order dependency**: a test relies on state a previous test left behind. Have each test set up and clean up its own state.
- **Network, time, and randomness**: a real network, clock, or random generator in the loop. Use a test double or a local instance, freeze the time, and seed the generator.

The same study found 78% of flaky tests were flaky from the day they were written <Cite id="luo-2014" form="parenthetical" />, so run a new test many times in a row before you merge it.

## Testing Tools

Pick the framework your stack's documentation uses, because that's the one its examples and tutorials assume. A short list of defaults:

- Python: [pytest](https://docs.pytest.org/en/stable/).
- JavaScript and TypeScript: [Vitest](https://vitest.dev/) or [Jest](https://jestjs.io/), with [Testing Library](https://testing-library.com/) for UI components.
- Java: [JUnit](https://junit.org/); Go: the built-in [`testing`](https://pkg.go.dev/testing) package.
- End-to-end, any stack: [Playwright](https://playwright.dev/).

Choose tools the team will run every day. A plain pytest suite that runs on every pull request catches more than an elaborate setup that only one person knows how to start.

## Best Practices

These keep a suite trustworthy once it's large enough that nobody remembers why each test exists:

- Hold test code to the same standard as production code, because a test nobody can read is a test nobody fixes when it fails.
- Fix a red suite the day it goes red; a suite that stays red for days teaches the team that red means nothing.
- Delete tests for removed features and dead code paths, which slow the suite and test nothing anyone depends on.
- Keep the suite fast enough to run before every push. When it slows down, find the few slow integration or E2E tests responsible and speed them up or move them to a separate job.

## Some Truths About Testing

Coverage is the metric most likely to mislead you, because it records which lines executed, not whether anything was checked; a suite that calls every function and asserts nothing reports excellent coverage. <Cite id="inozemtseva-2014" /> generated 31,000 test suites for five large Java systems and found only a low to moderate correlation between coverage and fault detection once suite size was controlled, and they suggest coverage should not be a quality target.

Mutation testing measures what coverage can't: whether the tests would notice a bug. Tools such as [PIT](https://pitest.org/) and [Stryker](https://stryker-mutator.io/) seed small faults into your code and count how many your tests catch, and <Cite id="just-2014" /> found that a suite's mutant detection correlates with its detection of real faults, independently of coverage. It reruns the suite once per seeded fault, so on a large codebase run it on the critical paths rather than everywhere.

Flaky tests do damage beyond the test itself. On Google's Testing Blog, <Cite id="micco-2016" /> reports that about 1.5% of all test runs at Google are flaky, that almost 16% of their tests have some flakiness, and that 84% of the pass-to-fail transitions their CI sees involve a flaky test; with that many false alarms, people commonly ignore legitimate failures in those tests. Deleting the test is tempting, but <Cite id="luo-2014" /> found that 24% of flaky-test fixes changed the code under test, and 94% of those fixed a real bug, so they argue against simply removing flaky tests. Quarantine a flaky test the day you find it, so it stops training the team to ignore red, then read the failure before you decide between fixing and deleting.

Testing pressure improves design only up to a point. What it rewards is separating decisions from side effects: a function that only computes is trivial to test, and one that computes and writes to a database is not, and the separated version is also easier to change. Past that point, tests push you toward over-abstraction, such as an interface that exists only so a mock can be injected, so when a change makes code easier to test and harder to read, make that trade deliberately.

Verification is easier to invest in than validation, because a test suite gives a green or red answer on every push and a user session gives a page of notes once. That asymmetry is how a project ends up with a green suite on a feature nobody wants: nothing in CI can tell you that you specified the wrong thing, and only a session with real users can.

## Testing in Industry and Academia

Google's testing culture turned on a failure. <Cite id="bender-2020" /> recounts that by 2005 the Google Web Server's releases were getting buggier, and at one point more than 80% of its production pushes contained user-affecting bugs that had to be rolled back; the tech lead then required tests with every new code change, run continuously, and within a year emergency pushes had dropped by half, despite a record number of changes.

In academia, testing is also a research field, and most of the studies on this page come from it. Testing research often measures a suite with mutation analysis, because the real faults in a program are usually unknowable in advance <Cite id="just-2014" form="parenthetical" />. When research depends on code, reproducibility plays the role a test suite plays in industry, and the failure it guards against has been documented at scale: <Cite id="kapoor-2023" /> surveyed the literature and found data leakage in 17 fields, affecting 294 papers and in some cases leading to wildly overoptimistic conclusions.
